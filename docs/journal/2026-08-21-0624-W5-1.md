# W5-1 — Loading, empty and error states, and the race that would have been dangerous

**Status:** DONE
**Files touched:** `web/src/latestOnly.ts` (new), `web/src/latestOnly.test.ts` (new),
`web/src/App.tsx`, `web/src/api.ts`, `web/src/index.css`, `BACKLOG.md`

## What I did

Four things, and one of them matters far more than the others.

### 1. A search in flight no longer blanks the page

Correcting a chip re-runs the search. Until now that made every trial card vanish
and reappear a second later. Now the previous results stay on screen, dimmed,
with *"Updating from ClinicalTrials.gov…"* above them and `aria-busy` set so a
screen reader knows too.

### 2. Failures say something a person can act on

`fetch` rejects with **"Failed to fetch"** when it cannot reach the server. That
is the browser talking to a developer. Every failure is now translated on the way
out — unreachable service, malformed search, upstream error — and each message
ends with something to do. There is a **Try again** button next to it.

I verified this by actually stopping the backend, not by reading the code. The
page showed *"The search failed (error 502). This is our end, not yours — trying
again may work."* I restarted the backend, clicked Try again, and got twenty
trials back.

### 3. The empty result says which kind of empty it is

Before: *"No recruiting trials came back for that search."* Now, one of two:

> No recruiting trials for "kuru" within 50 miles of Portland, Oregon. Widen the
> radius, or search "Anywhere" to see whether any exist at all.

> No recruiting trials anywhere matched "kuru". Registry records use clinical
> names — try the condition's medical name, or a broader one.

Both are real screenshots of the running app. The difference matters: one of
those problems is solved by moving a slider and the other never will be.

Note the message names the radius and place **the results were computed for**,
not whatever the chips say now — the app keeps the profile a result came back
with, so an empty message can't describe a search that never happened.

### 4. The race, which is the real content of this task

The page starts a fresh search on every chip correction, so two corrections mean
two searches in flight — and **HTTP makes no promise about which finishes
first.** Correct your age from 41 to 12, then immediately to 34, and the reply
for 12 can land last.

For most applications that is a flicker. Here it means the screen showing which
trials would rule out a twelve-year-old, underneath chips that say 34 —
eligibility verdicts computed for a person the user has already told us they are
not. Quietly, with no error, looking entirely normal.

`web/src/latestOnly.ts` fixes it in about ten lines: every search takes a ticket,
and when it comes back it asks whether it is still the newest. If not, its result
is dropped on the floor.

## Why I did it this way

**The guard lives in its own file, not as a `useRef` inside the component,
because a race cannot be verified by looking at the page.** That is the whole
reason `web/` got a test runner in D-5 — I started this task, realised criterion
(d) needed a test, stopped, set the task back to `READY`, did D-5, and came back.
There are now six tests on it, including one that reproduces the exact scenario
above: two tickets taken in order, and the answers checked in the wrong order.

**A counter and a comparison, not `AbortController`.** Aborting the older request
would also work and is what a lot of code does. It is more machinery — abort
signals threaded through the fetch layer, a rejection that has to be told apart
from a real error — to achieve the same thing. The result of a stale search is
harmless as long as nobody displays it, so not displaying it is the whole fix.

**Verifying the mid-flight state took a trick worth writing down.** My first
attempts to catch "results still on screen while updating" kept sampling *after*
the search had already finished — the backend caches registry responses, so a
repeat search came back in under 40 milliseconds. Sampling faster is a race
against a race. Instead I wrapped `window.fetch` in the page with a 1.5 second
delay and then sampled: 20 trials still on screen, `data-updating="yes"`,
`aria-busy="true"`, cards at 55% opacity, status text present. Then I confirmed it
settled cleanly afterwards. **If you cannot observe a state reliably, slow the
thing down rather than sampling harder.**

**`busy` cannot get stuck.** The `finally` only clears the spinner if this search
is still the newest — otherwise a stale reply landing late would clear a spinner
that belongs to a search still running. The newest search always clears its own,
and I checked the page settled to `aria-busy="false"` after the deliberately
slowed run.
