# D-3 — Two build runs can no longer work on this repository at the same time

**Status:** DONE
**Files touched:** `tools/runlock.py` (new), `tests/test_runlock.py` (new),
`justfile`, `CLAUDE.md`, `.gitignore`, `BACKLOG.md`

## What I did

This project is built by unattended runs that fire on a schedule. On 2026-08-21
two of them fired at once. The second one worked out by hand that the first was
alive, stood down, and nothing was lost — but "worked it out by hand" is not a
safety mechanism, it is luck. This task replaces the luck with a lock.

There is now one command a run types before it does anything:

```bash
just lock
```

If another run is alive, that command prints **STAND DOWN**, names the run that
holds the repository, says how long ago it was last seen, and exits with a
failure code. `CLAUDE.md` — the contract every run reads first — now says that a
failure there means write one line in the journal and quit. If no other run is
alive, the command succeeds and this run owns the repository until it runs
`just unlock` at the end.

**The interesting part is why it is not a normal lock.** The obvious tool is the
operating system's own file lock, `flock`. It cannot work here, and the reason is
worth being able to say out loud: *a scheduled agent run is not one program.* It
is dozens of separate short commands, one after another, each finishing before
the next starts. An OS lock is released the moment the program that took it exits
— so it would be gone between the first command and the second.

So the lock is a small file, `.runlock`, with a timestamp inside it, and a run
proves it is still alive by touching that timestamp after every commit
(`just tick`). A lock that nobody has touched for **90 minutes** is assumed to
belong to a run that died; the next run takes it over and is told to go and look
at the working tree, because a dead run may have left a half-finished task.

The one part that has to be exactly right is what happens when two runs ask at
the same instant. That is a single line: the file is created with the operating
system's `O_CREAT | O_EXCL` flag, which guarantees that if a thousand programs try
to create the same file simultaneously, exactly one succeeds and the rest are
told the file already exists. Everything else in the file is bookkeeping around
that one guarantee.

**How I know it works.** `tests/test_runlock.py` starts eight real competing
processes at once and asserts that exactly one is allowed to proceed and seven
are told to stand down. It does not call the function twice in a row and call
that a concurrency test. Twelve tests in total cover the takeover of a dead run's
lock, the refusal to take over a live one, a corrupt lock file ageing out instead
of blocking the project for ever, and the ordinary take/tick/release cycle. Full
suite: **91 tests passing**, up from 79. `just check` green.

I also used it for real, on this run, before writing this entry — took the lock,
watched a second attempt get refused, checked `just lock-status`. It is not just
tested, it is in service.

## Why I did it this way

**A timestamp file, not a process ID.** I could have stored the process ID of the
shell that took the lock and checked whether that process still exists. It would
be wrong here for the same reason `flock` is wrong: that shell exits seconds
later, so the check would report every live run as dead. The heartbeat measures
the thing we actually care about — has this run done anything recently — rather
than a proxy that does not apply.

**Ninety minutes, and a test that guards the number.** This is the one judgement
call in the module, so it is explained at the constant and pinned by a test. It
has to be longer than the gap between a live run's commits, or a working run gets
declared dead and trampled. It has to be shorter than the five hours between
scheduled runs, or a crashed run's lock survives to block its successor. Ninety
minutes clears both with room either side.

**A corrupt lock file counts as "someone might be there", but ages out.** If the
file cannot be read, the safe reading is that a run may exist, so we refuse. But
refusing for ever on an unparseable file would let one bad byte halt the project
until a human intervened, so its age is taken from the file's own timestamp and
it expires like any other. Refuse now, never refuse for ever.

**I edited `CLAUDE.md`, which I was warned about.** The previous run's summary
said an agent rewriting its own operating contract on another agent's suggestion
is not obviously right, and I agree — but a lock that nothing calls is worse than
no lock at all, because it looks like protection. D-3's own done-criteria name
`CLAUDE.md` as part of the task. I kept the edit to the mechanics of the loop:
take the lock at the start, tick after each commit, release at the end. **The
human should read that diff and is welcome to overrule it** — nothing else in the
build depends on the wording.

**The `DOING`-marker advice got simpler, not more complicated.** It used to say:
if you find a `DOING` task, check the git log and guess whether a peer is alive.
Now the run already knows, because it holds the lock — so a `DOING` marker found
while holding the lock definitely belongs to a run that died, and can be adopted.
The manual git-log check is kept as a second opinion for the case where the two
signals disagree, which would mean something neither of us predicted.

## What the next run should know

1. **Type `just lock` before you touch anything.** It is now the first
   instruction in `CLAUDE.md`. If it says STAND DOWN, believe it.
2. **`just tick` after every commit, `just unlock` at the end.** Forgetting
   `unlock` is not a disaster — the lock expires after ninety minutes — but a run
   that forgets leaves the next one taking over a "stale" lock and reporting a
   crash that did not happen.
3. **`.runlock` is gitignored and must stay that way.** It is state about this
   machine, not about the project. It will never show up in `git status`.
4. **This run took the lock at 08:27 UTC.** If you are reading this and
   `just lock-status` still shows that run as live, less than ninety minutes have
   passed and you should stand down.
5. The other half of D-3 — the `CLAUDE.md` paragraph about checking for a live
   peer — had already been done by the previous run in commit `a61dcb8`. I
   rewrote it rather than adding to it, because holding a lock answers the
   question that paragraph was telling runs to answer by hand.
