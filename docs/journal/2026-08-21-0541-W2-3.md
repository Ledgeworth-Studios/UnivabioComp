## What I did

Until now this project had no interface. This task builds the first one: a single
web page where you type a condition, say where you are and optionally a little
about yourself, press a button, and get back the trials recruiting near you.

Two commands run the whole thing:

```bash
just serve     # the Python API, in one terminal
just web       # the web page, in another
```

or `just dev` to start both at once. The page is at <http://localhost:5173>.

**I ran it in a real browser against the live registry, and it works.** Searching
"multiple sclerosis" near Portland as a 41-year-old woman returned six recruiting
trials, each rendered as a card. Two of the cards are worth describing because
they are the product's argument in miniature:

- A study of BRIUMVI for relapsing MS. It has **ninety-one sites** worldwide, and
  the card says: *Nearest site: TG Therapeutics Investigational Trial Site,
  Portland, Oregon — 0.6 miles away (of 91 sites)*. The registry lists Birmingham,
  Alabama first. A tool that showed the first site would have sent this person to
  Alabama.
- A paediatric MS trial. Its card says, in red: *This one is a conflict — this
  trial enrols ages 10 Years to 17 Years; you told us you are 41 years old*, and
  underneath, in smaller grey text, *Registry says: 10 Years to 17 Years*.

That second card is the whole idea. It does not say "no match" or show a 43%
score. It says what would stop you, in a sentence, with the registry's own words
printed underneath so you can check it.

The three checks each get one of three labels, and the wording of those labels
was chosen carefully:

| Verdict | What the card says |
|---|---|
| `MET` | "Nothing here rules you out" |
| `NOT_MET` | "This one is a conflict" |
| `UNKNOWN` | "Ask the study team" |

None of them says "you qualify". `MET` does not mean the person is eligible — it
means this particular field is not a barrier, which is a much smaller claim and
the only one we can support. That is rigor rule 1, in the interface rather than
in a comment.

Each card also carries the registry sentence behind every reason (rule 2), a link
to the trial's own ClinicalTrials.gov page with the date the record was last
updated (rule 5), and an expandable list of the trial's eligibility criteria in
the registry's own words — with a note saying plainly that they have **not** been
checked against your situation, because that is the part that needs a model and
it is not built yet.

Below the fold the page says: *Nothing you type here is stored or sent anywhere
else.* That is rigor rule 4, and it is true — the profile goes into one request
and is never written down.

## Why I did it this way

**The response types are written by hand, not generated.** FastAPI publishes an
OpenAPI schema, and there are tools that turn it into TypeScript automatically. I
wrote the forty lines instead. A generator is a build step, a dependency and a
thing to explain on camera, and the payoff is forty lines. If the two ever drift
apart, `npm run build` fails on the exact field that moved, because the build
runs the TypeScript compiler.

**The dev server proxies `/api` to the backend instead of the backend allowing
cross-origin requests.** Both work in development. Only one matches production:
W5-5 has FastAPI serve the built files, so the page and the API are the same
origin there. Proxying keeps development and production the same shape, and means
no CORS configuration exists to be got wrong or left too permissive.

**Every field about the person is optional and says so on screen.** The fieldset
is labelled "About you — every one of these is optional" and the age box's
placeholder reads "leave blank if you'd rather not say". A blank box sends `null`,
not zero, and the backend turns that into `UNKNOWN` and a question for the study
team. This is the one place where the product's argument could be accidentally
destroyed by a well-meaning "required" attribute.

**The location picker is a list of six cities, and I am flagging that as a
weakness rather than hiding it.** The registry needs a latitude and longitude, and
asking a person to type coordinates is not a product. Turning "Tucson" into
coordinates is geocoding: it needs a service, and choosing one has a privacy
question attached — the user's location should not be handed to something that
logs it against them. That is a decision the human should make, so it is now
**D-4** in the backlog with the constraints written down, and the code has a
comment saying the same. "Anywhere", which searches with no location at all, is
not a placeholder and should survive D-4: it is a legitimate query that returns
trials with no distance claim, which beats a distance we would have to invent.

**The web build gets its own CI job rather than joining `just check`.** A
Python-only task should not have to install node to find out whether it passed,
and a frontend-only task should not run the Python suite. But an unchecked
frontend rots, so `just web-check` — install, lint, type-check, build — now runs
on every push as a separate job. Same principle as D-1: the local command and the
CI command are the *same command*, not two lists that drift.

**I deleted the Vite template's placeholder art and README.** Those files were
created by the scaffold in this run, so removing them breaks no rule, and a judge
reading this repository should not find a page explaining what Vite is.

## What the next run should know

1. **`just dev` is the fastest way to see the whole thing working.** It starts the
   API in the background and the web page in the foreground, and stops the API
   when you stop it.
2. **The next `READY` task in file order is W2-4** — editable profile chips. Note
   that it says "correct any *extracted* field", and extraction is W2-1, which is
   blocked on the API key. The chips can still be built against the fields the
   form collects today; read the task before assuming it is blocked.
3. **`web/node_modules/` and `web/dist/` are gitignored** by the existing
   `node_modules/` and `dist/` rules. Nothing extra was needed.
4. **The verification was a real browser, not a screenshot of a mock.** Form
   submitted, `POST http://localhost:5173/api/search → 200 OK` recorded in the
   network log through the Vite proxy, six real trials rendered, no console
   errors. If you change the proxy or the response shape, re-do that check —
   `npm run build` will not catch a broken proxy.
5. **Nothing here is designed yet.** Colours, spacing and the mobile layout are
   deliberately plain. Week 5 owns that, and W5-3 owns the accessibility pass —
   the form has real labels tied to real inputs, which is a start, but it has not
   been tested with a screen reader and must not be described as accessible.
