# W1-2 — ClinicalTrials.gov client, with the "nearest site" trap proven on real data

**Status:** DONE
**Files touched:** `whynot/registry.py`, `tools/record_fixtures.py`,
`tests/conftest.py`, `tests/test_registry.py`,
`tests/fixtures/registry/search_ms_portland.json`,
`tests/fixtures/registry/study_NCT06251323.json`, `BACKLOG.md`

## What I did

This is the layer that talks to ClinicalTrials.gov. It is the boring, factual
half of the product: it fetches trial records and reshapes them, and it makes no
judgements about anybody.

**`whynot/registry.py`** does four things.

1. **Searches.** `client.search("multiple sclerosis", latitude=..., longitude=...)`
   asks the registry for recruiting trials for a condition within a radius. The
   registry's API version 2 needs no API key at all — it is public — so there is
   no secret anywhere in this code path.
2. **Fetches one trial** by its NCT number, the identifier you see on the
   registry website (`NCT06251323` and so on).
3. **Turns the JSON into typed objects.** `Study`, `Eligibility`, `Location`.
   The reason this is worth doing rather than passing raw dictionaries around is
   that the registry omits fields it doesn't have — a trial with no upper age
   limit simply has no `maximumAge` key — and a typed layer forces that to be
   handled once, here, instead of crashing somewhere in the UI six weeks from
   now.
4. **Caches every response in a SQLite file**, keyed by a hash of the exact
   request. Measured on a live call: 0.23 seconds uncached, 0.0007 seconds
   cached.

### The trap, and why it now has a test

`docs/PLAN.md` warns that the geographic filter matches the *study*, not the
*site*: if any one of a trial's locations is within your radius the trial comes
back — and the response then lists **every** location that trial has, anywhere in
the world. I recorded a real search around Portland, Oregon and checked. All five
trials that came back have a site 0.6 miles from downtown Portland. All five list
a site *first* that is thousands of miles away — Washington D.C., Loma Linda,
Birmingham, Los Angeles, Palo Alto.

So a naive implementation that showed `locations[0]` would tell a Portland user
that their nearest multiple-sclerosis trial is in Alabama, when in fact it is
across town. `Study.nearest_location(lat, lon)` computes the real answer with the
haversine formula, and
`test_nearest_location_is_not_the_first_location` asserts on the recorded data
that the first-listed site is *always* outside the radius while the nearest is
always inside it. If someone later "simplifies" this by taking the first
location, that test fails.

### Tests never touch the internet

`tools/record_fixtures.py` is a script you run by hand; it saves real registry
responses into `tests/fixtures/registry/`. The tests replay those saved files
through httpx's mock transport, so they exercise exactly the same parsing,
caching and URL-building code that production uses — the bytes just come from
disk.

`tests/conftest.py` adds a belt-and-braces guard: any test that manages to
construct a real HTTP client gets an immediate, loud failure telling it to record
a fixture instead. There is a test that checks the guard itself works, because a
safety net nobody tests is a safety net that quietly stopped working.

21 tests, all passing, in a tenth of a second.

## Why I did it this way

**Injected HTTP client rather than a `record`/`replay` library.** The alternative
was something like `vcrpy`, which intercepts requests and replays cassettes. It
would have been fewer lines. It also would have been one more dependency whose
behaviour the human has to explain on camera, and a magic layer between the test
and the code. Passing in `httpx.MockTransport` is four lines, uses only the HTTP
library already needed, and keeps a single code path — the test really does run
the client.

**Cache keyed by request hash, not by NCT number.** Keying by NCT number would
have been simpler but only works for single-study fetches; searches would need a
second mechanism. Hashing the canonical `GET /path?sorted=params` string handles
both with one table, and sorting the parameters makes the key independent of the
order they were built in (there is a test for that).

**Asking for a subset of fields.** The full record for one trial is large and
mostly irrelevant to us — it includes every outcome measure, the whole study
description, IPD sharing statements. `STUDY_FIELDS` lists the seven modules we
actually read. This keeps the recorded fixtures small enough to read by eye,
which matters because a fixture nobody can read is a fixture nobody checks. Note
the trade: if you add a field to a dataclass, you must add its module to
`STUDY_FIELDS` or it will silently come back as `None`. That warning is in the
code comment too.

**Deliberately boring retries.** Three attempts, sleeping one second then two, on
429 and 5xx only. A 404 is a real answer — the trial doesn't exist — and is
raised straight away rather than retried three times.

## What the next run should know

- **The fixture data is genuinely useful for W1-3.** `search_ms_portland.json`
  already contains five real age-bound shapes: `"22 Years"` with no maximum,
  `"10 Years"`–`"17 Years"`, `"18 Years"` with no maximum, `18`–`70`, `18`–`55`.
  W1-3 still needs a record with a *months* bound (`"6 Months"`) and one with no
  minimum at all — add those to `tools/record_fixtures.py` and re-run it rather
  than hand-writing JSON.
- **`NCT06251323` is recorded as its own fixture** because it is the trap-2
  example: its structured fields look like a perfectly ordinary patient trial
  (18+, all sexes, healthy volunteers accepted) and its criteria text is entirely
  about federally qualified health centres. Structured fields alone cannot detect
  this — only the criteria text gives it away. That is worth remembering when
  W3-4 (labelling non-patient trials) comes around.
- **Age strings are kept as raw strings here on purpose.** `Eligibility.minimum_age`
  is `"18 Years"`, not `18`. Parsing them is W1-3's job and it is more subtle than
  it looks (years, months, weeks, and absent bounds). I did not want two places in
  the codebase that both half-parse an age.
- The cache database is created wherever the caller asks for it and `*.db` is
  gitignored, so no cache file will ever be committed. `ResponseCache` is
  optional — `RegistryClient()` with no cache just always fetches.
- One live smoke test was run by hand (not part of the suite): search, cached
  re-search, and a single-study fetch all behaved as expected against the real
  API on 2026-08-21.
