## Read this bit first

**This page has not been tested with a screen reader, and must not be described
as accessible.** I can measure contrast, walk a tab order and read an
accessibility tree. I cannot put on headphones and listen to VoiceOver, and the
gap between "passes automated checks" and "usable by a blind person" is where
most accessibility claims die. What follows is the measurable part, done
properly, and it is a floor rather than a finish.

## What I found and fixed

### Contrast: my own prediction was wrong

The last journal entry said the muted grey used on every "registry says" line was
the pairing most likely to fail. **It wasn't.** Measured, it comes in at 5.48:1
on a card and 4.87:1 at its worst — comfortably over the 4.5:1 required. Every
one of the nineteen text pairings passed, unchanged.

What actually failed was something I hadn't suspected: **the border of every
input and select, at 1.33:1.** That border is the only thing on screen showing
where the control is, so WCAG holds it to 3:1, and `--line` at `#d8e0e8` was
nowhere near. Somebody with reduced contrast sensitivity would have been hunting
for the edges of the form.

Fixed by splitting one token into two, which is the honest distinction anyway:

- `--line` stays for **decorative** boundaries — panel edges, separators. Nothing
  about finding a control depends on seeing them, and WCAG does not require
  contrast for them.
- `--control-border: #7b8b9c` is for **the edge of a control**. It is the
  lightest colour I could find that clears 3:1 against every background a control
  sits on: 3.49 on white, 3.31 on the page, 3.21 inside a chip.

### The focus ring, and why `outline-offset` is load-bearing

There was no focus style at all, only the browser default. There is one now, and
one detail in it is not decoration:

```css
:focus-visible {
  outline: 3px solid var(--accent);
  outline-offset: 2px;
}
```

The primary button is *filled* with `--accent`. A ring drawn on that button in
`--accent` would have a contrast ratio of **1.0** against it — completely
invisible, on the most important control on the page. The 2px offset draws the
ring on whatever is behind the button instead, where `--accent` measures 8.54
against a card and 8.09 against the page.

`:focus-visible` rather than `:focus`, so clicking with a mouse does not leave a
ring behind — which is the usual reason somebody deletes the focus ring
altogether and breaks it for everyone.

There is also a `forced-colors` block, because Windows High Contrast Mode
discards authored colours: a transparent outline gets repainted by the operating
system, whereas one in our palette would simply vanish.

### The keyboard bug, which was the worst thing here

Editing a chip replaces its button with an input. When the edit finished, that
input was removed from the page and the browser — having nowhere to put the
focus — dropped it on the document body.

With a mouse you never notice. With a keyboard, **correcting one chip threw you
back to the top of the page**, and you had to tab all the way down again to
correct the next one. On a page whose entire premise is "correct anything we got
wrong", that is close to a broken feature.

Each chip's button now registers itself, and finishing an edit returns focus to
the button it started from. Verified in the browser: after committing an age
edit, `document.activeElement` is the "Change Age" button, not `<body>`.

### Announcing that the answer changed

Correcting a chip silently replaces every card. Somebody not watching the screen
had no way to know. The result count is now an `aria-live="polite"` region, so it
is announced at the next pause rather than interrupting.

### A heading level that was skipped

The printable summary opened with an `h2` and no `h1` anywhere — it replaces the
whole page, so the masthead's `h1` is not on screen. It is an `h1` now. Checked
across the whole document: h1 → h2 → h3 → h4, fifteen headings, **no skipped
levels**.

## Why I did it this way

**The tests read the real stylesheet, and there is a control proving they read
something.** `contrast.test.ts` parses `index.css` and computes the ratios, so a
future palette change cannot quietly make text unreadable — and it does not keep
its own copy of the colours, because a duplicate list drifts and then passes
while the page fails.

That test also caught me out in a way worth recording. My first version imported
the CSS through Vite's `?raw`, which is tidier — and **vitest stubs CSS imports
to an empty string**. Every assertion in the file passed while measuring
absolutely nothing. It now reads the file from disk, and there are three tests
whose only job is to prove the file was actually read: it is over 1000
characters, it contains the token block, and asking for a token that does not
exist raises rather than passing silently. *A test that cannot tell "all colours
pass" from "there are no colours" is not a test.*

**Verdict labels moved into their own module, and it is not just to quiet the
linter.** Each check has a coloured left border — green, red, amber. To somebody
who cannot distinguish those, or who is listening rather than looking, that
border is nothing at all, so the words carry the entire meaning (WCAG 1.4.1).
`verdictLabels.test.ts` pins that all three exist, are distinct, are sentences
rather than tokens, never name a colour, that `MET` never claims eligibility, and
that `UNKNOWN` does not say who should answer — because W3-3 established that
half the unknowns are the person's own to settle.

**Test type-checking got its own tsconfig project rather than a shortcut.** The
contrast test reads a file, which needs node's types, and the easy fix — adding
`"node"` to the app project — would let application code reach for node builtins
and still type-check. There is now a third project alongside the app and node
ones, and the app project explicitly excludes tests. Slightly more config, and it
keeps "browser code cannot use node APIs" a real rule.

## What the next run should know

1. **W5-3 is done to the limit of what an agent can honestly verify.** If the
   human wants a real accessibility claim for the submission, half an hour with
   VoiceOver (⌘F5 on this Mac) on the search → chips → results → print flow is
   the missing piece. The three things most likely to be wrong are the chips
   (buttons that swap into inputs), the live region wording, and whether the
   trial cards read in a sensible order.
2. **The next `READY` task is W5-4** — the rigor rules from `docs/PLAN.md` made
   visible in the interface. Most of the groundwork exists: the disclaimer is
   shown, every reason quotes its registry source, "nothing you type is stored"
   is in the footer. Read the plan's five rules and check each one is *visible*,
   not merely honoured.
3. **`--line` and `--control-border` are not interchangeable**, and there is a
   test that fails if the form's inputs are switched back to `--line`. The
   distinction is decorative versus load-bearing, and it is commented where the
   tokens are defined.
4. **54 frontend tests, 171 Python tests**, both gates green.
