### The one thing the human needs to act on

**W1-5 is the task that could sink the project, and it is waiting on you.** It
asks whether a model can read real eligibility prose and return coherent
`MET` / `NOT_MET` / `UNKNOWN` verdicts. Answering it needs real API calls, and
this machine has no key: `ANTHROPIC_API_KEY` is unset and a direct call to
`api.anthropic.com` returns `401 authentication_error`.

Put a key where the scheduled run can see it — in the shell profile the task
inherits, or a `.env` file in the repository root (already gitignored, and it must
stay that way) — and the next run can pick W1-5 straight up. Everything it needs
is built: real trials, a person, the structured fields already decided, and
criteria split with verbatim quotes.

### Two things found in the data that will matter later

Both are recorded properly in the earlier journal entries, but they are the sort
of thing worth being able to say on camera:

- **The registry's geographic filter is a trap, and it is now proven on real
  data.** Searching within 50 miles of Portland returned five trials. All five
  have a site 0.6 miles from downtown Portland. All five list a site *first* that
  is thousands of miles away. Showing the first location — the obvious
  implementation — puts an Alabama clinic at the top of a Portland user's results.
  There is a test that fails if anyone ever does that.
- **The eligibility text is far messier than a demo would suggest.** Across
  seventeen real trials: headers written as bullets, headers appearing four times
  (cases and controls), markdown-escaped numbering, roman-numeral sub-items,
  ages measured in hours, and records with no headers at all.

## Why I did it this way

**I stopped at W1-5 instead of building it blind.** I could have written the judge
module, the prompt, the schema and fake-client tests, and left it for a run with a
key. I decided that was worse than nothing. W1-5's done-criteria are about the
*output* — "run it against five real trials and paste the output" — and a
finished-looking `judge.py` would invite the next run to just execute it rather
than do the genuine evaluation the backlog asks for. The prompt should be designed
by whoever can watch real verdicts come back.

**I did not go looking for a credential elsewhere on this machine.** Other tools
have stored credentials here. Using them would have produced a spike that works
for the agent and fails for the human, with a key that was not this project's to
spend.

**I marked W1-6 and W2-1 `BLOCKED` too, rather than leaving them `READY`.** A
`READY` task is one a run can finish. Left alone, the next scheduled run would
have taken W1-6, rediscovered the same 401, and lost its turn.

**I did D-1 out of file order, and skipped Week 2 to do it.** After W1-5 the next
`READY` task was W2-2, the FastAPI backend. Building the product's plumbing before
the question "does the judgement work at all?" has been answered contradicts the
stated goal of Week 1 — the backlog's own header says "prove the pipeline… No
UI." D-1 was unblocked, cheap, and made every future push verified. Recording the
deviation here so it is visible rather than silent.
