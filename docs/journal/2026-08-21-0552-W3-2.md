# W3-2 — Results are now ordered for the person searching, and nothing is hidden

**Status:** DONE
**Files touched:** `whynot/ranking.py` (new), `tests/test_ranking.py` (new),
`docs/decisions/0002-ranking-order-and-phase.md` (new), `whynot/api.py`,
`tests/test_api.py`, `BACKLOG.md`

## What I did

Until now the search returned trials in whatever order ClinicalTrials.gov felt
like. Now they are ordered for the person who asked, by four rules applied in
order:

1. **Trials with no conflict first.** A conflict means the person's own stated
   age or sex falls outside the trial's stated bounds.
2. **Then nearest first**, measured to the closest site.
3. **Then phase**, as a tie-break — see below, this is not advice.
4. **Then the NCT number**, so the order is total and two identical searches can
   never come back differently.

Here is the same live search, run twice, changing only the age:

```
--- age 41, near Portland ---           --- age 12, near Portland ---
 1. ok       NCT06655896  PHASE2         1. ok       NCT06408259  ages 10-17
 2. ok       NCT04047628  PHASE3         2. CONFLICT NCT06655896  ages 18-70
 3. ok       NCT06846281  PHASE3         3. CONFLICT NCT04047628  ages 18-55
 4. ok       NCT06433752  18+            4. CONFLICT NCT06846281  ages 40-70
 5. ok       NCT06441617  22+            5. CONFLICT NCT06433752  ages 18+
 6. CONFLICT NCT06408259  ages 10-17     6. CONFLICT NCT06441617  ages 22+
```

Six trials both times. **Not five.** The trials that conflict are still there,
still explained, just at the bottom — and that is the decision worth defending on
camera.

## Why I did it this way

**Conflicting trials are ranked down and never removed.** This is written up
properly in `docs/decisions/0002` because it is the opposite of what every other
trial finder does, and a later run will be tempted to "clean up" the results.

The argument is short. This project is called *Why Not This Trial*. A person who
searches and sees four results cannot tell whether a fifth was dropped for a
reason they could have argued with — a birthday next month, a sex field answered
too quickly, a diagnosis recorded under a different name. A person who sees five,
with one marked *"this trial enrols ages 10 Years to 17 Years; you told us you
are 41 years old"*, knows exactly what happened and can decide for themselves
whether it is worth a phone call.

There is a second reason, and it is about honesty rather than product design. The
conflicts this code can see are the three *structured* fields — age, sex, healthy
volunteer. The eligibility section of a real trial runs to a dozen paragraphs
that nothing has read yet. Hiding a trial on the strength of three fields would
imply a confidence the code does not have.

**Phase is a tie-break and I refused to let it be advice.** Sorting by phase in
either direction can be read as a recommendation: earliest-first reads as "newest
science", latest-first reads as "safest". Both are claims about which trials are
better to join, and `CLAUDE.md`'s hard rules say never to invent medical logic —
a sort order is logic. But two trials with the same conflict status at the same
distance still need *some* order or the list shuffles between identical searches.
So phase is used, ascending, in the registry's own enumeration, on the narrow
ground that it is more meaningful than alphabetical and it is reproducible. The
module says so where the code is, the decision record says so at length, and if
the human wants it the other way round it is one line and one test.

**Unknown sorts last, everywhere.** A trial with no located site has an unknown
distance, not a distance of zero, and a trial with no phase has no phase rather
than the first one. If unknown sorted first, a trial we know nothing about would
outrank a clinic nine miles away — wrong, and wrong in a way that would look
deliberate rather than like a bug.

**The tests build small studies by hand instead of using recorded fixtures.**
Ranking is about relationships between trials: this one conflicts, that one is
nearer, these two are identical except for phase. A fixture that happens to
contain the right combination today stops testing anything the day someone
re-records it. So most of the twenty-one tests construct exactly the situation
they are about. One test at the end runs the real recorded Portland search and
checks the paediatric trial sinks to the bottom, which is what ties the synthetic
tests to reality.

**One test deliberately checks that the test is testing something.** The
endpoint-level test asserts the returned order matches the ranking module *and*
that it differs from the registry's own order. Without that second assertion the
test would still pass if ranking were silently removed and the registry order
happened to match.

## What the next run should know

1. **`rank_studies` recomputes the hard filters that `build_trial` also
   computes.** That is deliberate — it keeps ranking a pure function of
   (studies, profile, coordinates) with no state threaded through the endpoint —
   and it costs nothing, because the filters are arithmetic on already-parsed
   data. Do not "optimise" it into a shared cache without a measurement showing
   it matters.
2. **The next `READY` task in file order is W3-3, the coordinator questions.**
   Think about whether it is blocked before starting: its input is the `UNKNOWN`
   verdicts, and *some* of those exist today from the structured filters ("you
   didn't tell us your age", "this trial doesn't say whether it accepts healthy
   volunteers"). The much larger source of `UNKNOWN`s is the judge, which is
   still waiting on the key. There is a real half-task here, the same shape as
   W2-2 — but read it and decide on its own words.
3. **The live registry has drifted from the recorded fixture.** The Portland MS
   search returned five studies when the fixtures were recorded and returns six
   now (`NCT06846281` is new). Nothing is broken — tests use the fixture, and the
   fixture is a snapshot on purpose — but if you compare a live run against a
   test expectation and the counts differ, that is why.
4. **`docs/decisions/0002` is the first decision record since 0001.** If you make
   a judgement call that a reasonable person could make differently, that is
   where it goes, and the backlog task should point at it.
