## What I did

Everything built so far — the registry client, the age/sex filters, the criteria
splitter — was a set of Python functions with no way to reach them except by
opening a Python prompt. This task puts a web API in front of them, so the
frontend (W2-3) has something to talk to.

Two commands and it runs:

```bash
just install
just serve
```

That serves <http://127.0.0.1:8000>. There is also a page at `/docs` that FastAPI
generates by itself, where every endpoint can be tried from the browser with no
code — worth knowing about for the demo video, because it makes the API tangible
on camera in about ten seconds.

There are two endpoints. `GET /api/health` says whether the server is up.
`POST /api/search` is the real one: you send a condition, where you are, and
whatever you chose to say about yourself, and you get back the recruiting trials
near you. For each trial the answer contains:

- the registry's own facts — title, status, phase, sponsor, enrolment, the date
  it was last updated, and **a link to the trial's own page** so nothing depends
  on our copy staying fresh;
- the three structured-field checks, each with a verdict of `MET` / `NOT_MET` /
  `UNKNOWN`, a plain-English reason, and the registry wording it came from;
- every eligibility criterion, split into separate lines, tagged inclusion or
  exclusion, each carrying the **exact** original text so the interface can quote
  the registry rather than paraphrase it;
- **the site nearest to you**, with its distance in miles.

That last one is the trap `docs/PLAN.md` warns about, and it is worth being able
to describe out loud. ClinicalTrials.gov lets you filter by distance — but the
filter picks which *studies* match, and then hands back **every site that study
has, anywhere in the world**, in its own order. One of the trials in the live run
below has ninety-one sites and lists Birmingham, Alabama first. The obvious
implementation shows the user Alabama. We compute the distance to each site from
the user's coordinates and show the closest, which for that trial is a clinic 0.6
miles from downtown Portland.

## Why I did it this way

**I split the task before starting it, and that is the main decision here.** W2-2
said "FastAPI backend exposing search **+ judge**". There is no judge: W1-5 is
blocked on a missing `ANTHROPIC_API_KEY`, so no run could have finished W2-2 as
written. Leaving it `READY` would have cost some future run its turn — exactly
what happened to W1-6 and W2-1 before they were marked blocked. So W2-2 is now
the deterministic search path, and the judge endpoint is **W2-2b**, `BLOCKED` on
the key. Nothing was dropped; the work was cut where the blocker actually falls.
The original line also had no done-criteria at all, which the backlog's own rules
require, so both halves now have criteria a stranger could check.

**Three tests exist to stop this module quietly becoming something else.** The
plan's central architectural claim is that only one step in the pipeline may use
a model, and everything else is plain Python. Claims like that decay silently. So
there is a test that reads `whynot/api.py`'s source and fails if the words
`anthropic`, `ANTHROPIC_API_KEY` or `openai` ever appear in it; a test that no
model client is imported; and a test that no field of any response ever tells a
person they are eligible.

That last test caught something on its first run, which is the sort of thing
worth admitting. It scanned the whole response for the phrase "you are eligible"
— and found it, in our own disclaimer, which says the tool *cannot tell you
whether you are eligible*. The test was too blunt, not the code. It now scans the
trial data only, where that phrase is never acceptable, and the disclaimer is
explicitly the one exempt place. A test that fails on the correct behaviour would
have been switched off within a week.

**The geo test counts how many cases it actually checked.** It asserts that the
site we return is not the first site the registry listed — but that assertion
only means something if the fixture contains studies whose first site is far
away. So the test counts the cases it inspected and asserts the count is five,
all five studies in the fixture. Without that line the test could pass by
checking nothing at all, and would still look green forever.

**The registry client is injected rather than created inside the endpoint.** That
is what lets the tests serve recorded fixtures through the identical code path
production uses — same parsing, same caching, same URL building, only the bytes
come from disk. It is four lines of FastAPI's dependency mechanism and it is the
reason the test suite can be honest about covering the real path.

**Results come back in the registry's order, and the response says so.** Ranking
is W3-2 and I did not do it here. Sorting results is easy to slip in and then
nobody knows which task did it.

**A registry outage returns `502`, not `500`.** If ClinicalTrials.gov is down,
that is not our bug and not the user's fault, and the message says which upstream
failed. Someone will hit this during the demo.

## What the next run should know

1. **W2-3 (the React frontend) is now unblocked and is the next `READY` task in
   file order.** It has a real API to call: `POST /api/search`, shape documented
   at `/docs` when the server is running, example curl in the README.
2. **The judge endpoint is W2-2b and is `BLOCKED`.** When the key arrives, do
   W1-5 first (it is the go/no-go — find out whether the verdicts are any good
   *before* wrapping them in HTTP), then W2-2b.
3. **`.registry-cache.db` appears in the repository root when the server runs.**
   It is the response cache, it holds public registry payloads only and nothing a
   user typed, and it is gitignored by the existing `*.db` rule — verified with
   `git check-ignore`. Do not commit it and do not be alarmed by it. Note that
   `ls *.db` will not show it, because the name starts with a dot.
4. **There is one warning in the test output** — Starlette says using `httpx`
   with its test client is deprecated in favour of `httpx2`. It is a deprecation,
   not a failure, and chasing it would mean changing the HTTP library the
   registry client is built on. Leave it; revisit only if it becomes an error.
5. **Nothing about the person is stored anywhere.** The profile arrives in the
   request body, is used for one search, and is never written to disk. That is
   rigor rule 4, and W5-4 has to make it visible in the interface too.
