## The usage policy is most of this task

Nominatim is the OpenStreetMap Foundation's geocoder: free, no key, no account.
It also runs on donated servers with, in their words, "very limited capacity", and
their usage policy shapes this code more than the problem does. I read it before
writing anything, which the task told me to do and which turned out to matter.

**"An absolute maximum of 1 request per second."** Enforced in code, behind a
lock, with a test that drives it through a fake clock and asserts the waits
actually happen. A rate limit that is documented and not implemented is one that
gets exceeded by the first impatient user — and it is not my project that gets
blocked, it is a charity's server that gets hammered.

**"Auto-complete search" is explicitly forbidden.** So there is a button, and
nothing is wired to a keystroke. I verified this rather than asserting it: in a
real browser I instrumented `fetch`, typed `T`, `Tu`, `Tuc`, `Tucs`, `Tucso`,
`Tucson` with pauses between, and counted **zero requests**. Pressed Find:
**one**. It is also why the *chip* for the place offers only places already known
— editing a chip is keystroke-driven and a lookup does not belong there.

**A User-Agent identifying the application**, because generic library defaults are
explicitly not acceptable. **Attribution displayed** next to the results, as the
ODbL requires.

## Two decisions worth defending

**The server geocodes, not the browser.** The browser could call Nominatim
directly and save a hop. It would also hand a third party the user's IP address
alongside the name of the town they are searching near — a service the user never
chose to talk to, learning where they are and what they are looking for. Going
through our server means OpenStreetMap sees *this server* asking about a town and
nothing about who wanted to know.

**The cache is in memory and never touches disk.** The policy asks clients to
cache. `docs/decisions/0005` turned off the registry cache because a file of
queries with timestamps is a record of what people searched for — and a file of
*place names* with timestamps is a record of where they were looking, which is
worse. So the cache lives in the process and dies with it: a repeated search makes
no repeated request, and nothing is written down. There is a test that runs two
identical searches in an empty directory and asserts one request and no files.

## The bug this nearly introduced

The profile stored the place as an **index into the six-city list**. The moment
that list could grow, the index stopped meaning anything on its own: search for
Tucson, get index 7, and every reader that still consulted the six-item constant
fell back to `PLACES[0]` — "Anywhere" — and searched **the whole world without
telling anybody**. The chips would have said Tucson. The results would have been
global. Nothing would have looked wrong.

I caught it from a compiler warning about which list was being indexed, not from
the UI, which is worth noting: the interface would have looked entirely correct.

The fix is not a bounds check. **The profile now holds the place itself**, so
there is no index to be stale. That removes the class rather than the instance,
and it is the thing to watch for whenever a fixed list becomes a growing one.

## Why I did it this way

**Rule 4's wording had to change, and that is the easiest thing here to forget.**
A typed place name now goes somewhere new, so the on-screen statement names
OpenStreetMap as well as ClinicalTrials.gov. Leaving it mentioning only one would
have made it exactly the kind of half-true claim that `docs/decisions/0005` was
written about — and I would have written it myself, four tasks after writing that
decision. There is a test pinning the word "OpenStreetMap" into rule 4.

**The presets survive as a fallback**, and the error message when the lookup fails
says so — *"You can pick a city from the list instead"* — rather than leaving
somebody stuck in front of a dead text box.

**The fixture recorder rate-limits itself too.** `tools/record_geocode_fixtures.py`
sleeps between queries. It would be a poor showing to obey a usage policy in the
application and ignore it in the tool that talks to the same service.
