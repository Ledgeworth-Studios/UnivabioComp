# D-7 — "Nearest site" could be a site that had already shut

**Status:** DONE
**Files touched:** `whynot/registry.py`, `whynot/ranking.py`, `whynot/api.py`,
`web/src/api.ts`, `web/src/TrialCard.tsx`, `web/src/PrintableSummary.tsx`,

## What I did

I started this run with nothing to do. The backlog had no `READY` task — the two
previous runs both reported that — so I did the only thing left worth doing:
I ran the app the way a judge will run it, and looked at what came back.

The first search I tried was multiple sclerosis near Tucson. The top result said:

> Nearest site: Research Site, Tucson, Arizona — 2.8 miles away

That sentence was false in the way that matters. The trial as a whole was
recruiting, but **that particular site had withdrawn** — it never enrolled anyone
and never will. The nearest site actually taking part in that study was in
Seattle, 1,218 miles away. A person in Tucson reading our page would have come
away believing there was a trial they could join a five-minute drive from their
house.

ClinicalTrials.gov publishes two different facts that are easy to confuse: the
status of the **study** and the status of each individual **site**. A study can
be "recruiting" overall while a third of its sites are withdrawn, finished, or
not open yet. We were reading the study's status and ignoring every site's.

Worse, we were doing it twice over. The site's status was already in our data —
the server fetched it, put it in the response, and handed it to the interface,
and **both** places that draw a site threw it away. And because we sorted results
by "distance to the nearest site", a trial whose nearest door was locked would
outrank a trial whose nearest door was open. The shut ones floated to the top.

I measured it before fixing it, so the size of the problem is a number and not an
impression: six live searches, three conditions across two cities, 112 trials
that had a nearest site. **18 of them — one in six — showed a nearest site that
was not recruiting**, with nothing on screen to say so.

Three changes:

1. **The registry layer learned the difference.** A site now knows whether it is
   enrolling, and a study can be asked for its nearest *enrolling* site as well as
   its nearest site full stop. Both questions are worth asking, so both exist.
2. **The results say which is which.** Under the distance, every trial now says
   what that site's own status is — "enrolling now", "not open yet", "withdrawn —
   this site never enrolled anyone" — and when the nearest site is shut, it also
   gives the nearest one that is open, with its distance. Shut sites are shown in
   the same red the interface already uses for a conflict. This is on the printed
   sheet too, because that is the page someone carries to an appointment.
3. **The order changed to match.** Results are ranked by how far away the nearest
   site you could actually join is.

On the search that started all this, the two trials with a shut Tucson door moved
from positions 1 and 2 down to 4 and 5, and three genuinely open trials took their
place. Nothing was hidden — both are still listed, now with the truth attached.

## Why I did it this way

**I did not hide non-recruiting sites, and that was a real choice.** Dropping them
would have made the bug disappear in one line. `docs/decisions/0003` already
settled that this tool labels rather than hides, and it is right here for a
specific reason: "there is a site 2.8 miles from you and it has withdrawn" is a
true and useful thing to know. It tells you this trial has a presence in your
city, which is worth asking the study team about — they may know something the
registry has not been updated with. Deleting the row would have thrown that away
to make a number look better.

**I translated the registry's vocabulary, but I refused to guess.** `NOT_YET_
RECRUITING` and `ACTIVE_NOT_RECRUITING` are precise and nearly unreadable, and
showing them raw is part of how somebody ends up thinking a withdrawn site is
somewhere to go. So there is a small table turning the ones we know into plain
English. Anything **not** in that table is printed exactly as the registry wrote
it, prefixed "registry status:". Inventing a friendly meaning for a code we do not
recognise is precisely the made-up certainty this project exists to avoid, and
there is a test that fails if someone later makes it guess.

**`ENROLLING_BY_INVITATION` counts as not open.** You cannot enrol yourself in one
of those by ringing up. Treating it as open would put a door in front of somebody
that does not have a handle on their side.

**Where nothing is enrolling anywhere, the trial keeps its real distance** rather
than being flung to the bottom of the list with the ones we know nothing about.
The ordering is a presentation choice, not a verdict about the person.

**On the tests:** I wrote them against studies built by hand rather than recorded
fixtures. The thing under test is a *relationship* — a shut site nearby and an
open one far away — and that is a coincidence of whatever the registry holds on
the day a fixture is recorded. A recorded fixture would quietly stop testing this
the next time somebody re-recorded it. The web test reads the two components off
disk and checks they mention the fields, which is the same technique
`contrast.test.ts` and `rigor.test.ts` already use; the alternative was adding a
component-rendering library to this project to assert on two lines of JSX, and
that costs more explanation than it buys.

**Then I checked the tests actually bite.** This codebase's recurring defect is
something built, plausible, and read by nothing — and a test that passes whatever
you do is the purest form of it. So I broke the fix three ways on purpose: made
ranking sort the old way, made every site claim to be recruiting, and stopped the
card printing the status. Each one turned a test red. Then I put it all back and
re-ran both gates.

## What the next run should know

**This came out of running the product, not reading the code.** Two runs before
me correctly found no `READY` task, verified the handover, and stopped — and the
state they verified was all true. But every claim they checked was one the
repository makes about *itself*: tests pass, CI is green, the tree is clean. The
bug was sitting in the first search anybody would type, and no test could have
caught it because no test knew site status was a thing. If you also find an empty
backlog: **run the thing and look at the output.** That is where the next one will
be too.

**Both environment blockers are unchanged, and I re-checked both.** There is still
no `.env` and no `ANTHROPIC_API_KEY` in the environment a scheduled run inherits,
so the nine model tasks stay blocked. `docker pull python:3.12-slim` still hangs
with no output — I killed it at 90 seconds, exactly as the last two runs recorded
— so `W5-5c` stays blocked. Do not go hunting for credentials belonging to other
tools on this machine; `W1-5`'s own note forbids it.

**A trap I hit, since the last run left a note about a similar one.** `timeout` is
not on macOS — `timeout 90 docker pull …` fails with "command not found", and if
you pipe it to `tail` the pipeline's exit code is `tail`'s, which is `0`. My first
Docker check therefore looked like a clean success and meant nothing at all. That
is the third variant of the same mistake in this journal: read the exit code of
the command you actually care about, not of whatever ran last.

**The screenshot tool returned blank images** while I was checking the interface,
though it had worked minutes earlier. I verified the rendering through the page's
own DOM instead — the visible text, and the computed colour of the shut-site line
(`#a4342a`, the token the contrast test already covers). That is better evidence
than a picture anyway, but if you try to screenshot this app and get a blank
frame, it is not your change.

**Where this leaves the build.** Still finished up to the point where it needs a
human, and the three things waiting on you are unchanged: put an API key in
`.env`; review the six eval labels flagged `needs_human_review` in
`tests/fixtures/eval/criteria_v1.json`; build the container somewhere with
registry access, deploy it, and record the video. `W6-4` is human-only — never
attempt it.

**One thing worth putting in the demo.** This is a good story for the "Health
Impact & Rigor" score, and it is short: the tool told a person there was a trial
2.8 miles away, the site had withdrawn, and we found it by running our own product
instead of our own test suite. The fix does not hide the shut site — it tells you
it is shut and where the nearest open one is.
