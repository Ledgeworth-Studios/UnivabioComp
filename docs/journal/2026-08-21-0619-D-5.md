## What I did

Everything under `web/` was checked by the TypeScript compiler, the linter, and
me clicking around a browser. That was fine for a skeleton and had stopped being
fine: `profile.ts` holds real logic now, and three components read it.

There is a test runner — **vitest**, which is Vite's own, so it needed no
configuration at all beyond `"test": "vitest run"` — and **11 tests**. `just
web-check` runs them, and because CI runs `just web-check` rather than its own
list of commands, they started running in CI without the workflow being touched.
That is the same principle D-1 set up for Python: the local gate and the remote
gate are the *same command*, so a step added to one is added to both.

## The mistake the tests exist to prevent

Almost all of them protect one rule: **a field the person has not stated is
`null`, and stays `null` all the way to the search request.** Not zero. Not an
empty string.

It sounds like pedantry. It is one careless `?? 0` away from being the worst bug
this application could have. If an unstated age became `0`, the tool would quietly
decide the user is a newborn, and a newborn is `NOT_MET` against the age bounds of
essentially every adult trial in the registry. A person who chose not to give
their age would be told they don't qualify for anything — a `NOT_MET` where the
truth is `UNKNOWN`, the error `docs/PLAN.md` says to weight above all others,
delivered silently and at scale.

So there are tests asserting the null survives into the request, that clearing a
chip puts it back, and — from the other direction — that **a stated age of zero is
kept as zero**, because a newborn is a person and confusing a real `0` with
silence is the same bug seen from the other side.

The rest cover the things that would break the chips quietly: that unstated fields
come back with no value so a chip can render them as "not said", that the
condition is not clearable because a search needs one, that choosing "Anywhere"
sends no coordinates rather than an invented pair, and that an out-of-range place
index falls back instead of crashing.

One test is a little unusual and worth keeping: it walks every key of the profile
object and asserts each one appears as a chip. A field that exists but is never
shown is a field the person cannot correct, which defeats the point of the chips
entirely — and adding a field without adding it to the display is exactly the sort
of thing that happens on a Tuesday.

## Why I did it this way

**I did this task out of file order, and stopped a task to do it.** I had marked
W5-1 `DOING`, written its done-criteria, and realised the fourth one — that a
stale search response must never be displayed — is a race condition, and a race
cannot be verified by looking at a page. It needs a test, and there was no test
runner. Rather than quietly install vitest inside W5-1 and break the
one-task-per-commit rule, I set W5-1 back to `READY` with a note naming D-5 as its
prerequisite, committed that, and came here. Nothing had been built, so nothing
was lost.

**Vitest, because it is Vite's own test runner.** The project already builds with
Vite. Vitest reads the same config, needs no separate build pipeline, no
transform configuration and no Babel. That matters here beyond convenience — the
competition rules require the entrant to walk judges through this code, and "the
test runner is the build tool's test runner" is a one-sentence explanation.

**No component rendering tests.** Testing that a heading says the right words
would need a DOM library and would break on every change Week 5 makes to the
layout, which is all of it. The tests are on the data — the part that has rules
and consequences.
