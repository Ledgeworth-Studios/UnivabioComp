## What I did

The API now serves the built web page itself. One process, one port, one origin:

```bash
just web-check   # builds web/dist
just serve       # serves the API *and* the page on :8000
```

Open <http://localhost:8000> and the whole thing is there. I ran it and searched
against the live registry through it — six trials, the disclaimer, all five rigor
notes, no console errors.

Four behaviours, each with a test:

- **`/` returns the page.**
- **Any unknown path returns the page too**, because a single-page interface owns
  its own routing. Without this, reloading the browser on anything but the root
  gives a 404.
- **`/assets/*` serve the built JavaScript and CSS.**
- **An unknown `/api/...` path is a JSON 404, not the page.** This one is easy to
  get wrong: hand *every* unknown path to the page and a mistyped API route
  returns HTML with a 200, leaving the caller parsing a web page as JSON and
  wondering what on earth happened. `/api/serch` returns
  `{"detail": "No such endpoint: /api/serch"}`.

**Why one origin matters, and it is not convenience.** The alternative is
enabling cross-origin requests on the API — and a CORS policy is a thing somebody
loosens one afternoon to unblock a colleague and never tightens again. Serving
both from one origin means the question never arises. There is no CORS
configuration anywhere in this project, and there is a test asserting that
`CORSMiddleware` and `allow_origins` appear nowhere in the API module. The dev
server has proxied `/api` since W2-3 for exactly this reason: development and
production have the same shape.

If `web/dist` is missing, the mount is skipped and the API starts normally, so
Python-side work never requires npm to have run.

## The part I did not do, and will not pretend to

**The Dockerfile has never been built.** I wrote it, and it is committed, and
nothing should assume it works.

Docker is installed here and I started the daemon successfully. It cannot reach
Docker Hub. `docker build` fails at `load metadata for
docker.io/library/python:3.12-slim` with `DeadlineExceeded: context deadline
exceeded`; a bare `docker pull python:3.12-slim` produces no output at all and
never finishes. There is no python or node base image cached locally to fall back
on — I checked the full list.

I wrote this task's own done-criteria before starting, and they said: *"the image
is actually built and run, and a real search performed against it — **not a
Dockerfile that looks right**."* That was the right thing to demand and I am not
going to quietly drop it now that it is inconvenient. So the container is
**W5-5c**, marked `BLOCKED`, with the exact error recorded and a note that a
two-stage build which has never run once is a draft — whoever builds it should
expect to fix something, and should specifically check the two claims in it that
have never been exercised: that it runs as a non-root user, and that `web/dist`
really arrives from the build stage.

**Publishing to a public URL stays `W5-5b`, human only.** This machine has no
hosting account and no hosting CLI, and putting the entrant's work on the public
internet is the entrant's decision, not an agent's.

## Why I did it this way

**Two stages in the Dockerfile, so node is not in the running image.** The tools
that build the page have no business in production: node and its packages live in
the first stage, and only `dist/` crosses into the second. `npm ci` rather than
`npm install`, because it installs the lockfile exactly and fails instead of
quietly resolving something newer — a build that can drift is not one you can
reproduce for a judge.

**No API key in the image, and a comment saying so.** The search path genuinely
needs no credentials — ClinicalTrials.gov v2 is public — and when the judge
endpoint arrives its key belongs in the runtime environment, never baked into a
layer. `.dockerignore` keeps `.env`, `*.db`, `.git` and `node_modules` out of the
build context entirely.

**`tests/` and `tools/` are excluded from the image.** The eval set, the fixture
recorder and the run lock are development things. Shipping them would put the
recorded registry fixtures into a production image for no reason.
