# W2-4 — You can now correct anything the app thinks it knows about you

**Status:** DONE
**Files touched:** `web/src/profile.ts` (new), `web/src/ProfileChips.tsx` (new),
`web/src/App.tsx`, `web/src/index.css`, `BACKLOG.md`

## What I did

The page now shows a row of chips headed **"What we're searching with"**:

    CONDITION multiple sclerosis   NEAR Portland, Oregon   WITHIN 50 miles
    AGE not said     SEX RECORDED AT BIRTH not said     HEALTHY VOLUNTEER not said

Click any chip and you can change it in place. Change one and the search re-runs
against the corrected version. The three about-you chips have an **×** that puts
them back to "not said", which is a real answer and not a blank.

The chips a person hasn't filled in look different on purpose — dashed outline,
grey italic text — rather than being hidden. Hiding an unknown field makes the
gap invisible. Showing it makes the offer: tell us if you like, or don't, and
underneath, in words:

> Anything marked *not said* is not held against you. It becomes a question to
> ask the study team, never a reason you were ruled out.

**The demonstration that this works is worth watching, because it is the whole
product in about fifteen seconds.** I did it in a browser against the live
registry:

| Age chip | The paediatric MS trial (`NCT06408259`, ages 10–17) | The fatigue trial (`NCT06441617`, ages 22+) |
|---|---|---|
| *not said* | Ask the study team | Ask the study team — "You didn't tell us your age." |
| `41` | **This one is a conflict** — "enrols ages 10 Years to 17 Years; you told us you are 41 years old" | Nothing here rules you out |
| `12` | Nothing here rules you out — "which includes 12 years old" | **This one is a conflict** |
| cleared | Ask the study team | Ask the study team |

Same six trials, same registry data, three different honest answers depending on
what the person chose to say — and when they say nothing, the answer is a
question, never a rejection. No console errors at any point.

I also changed what the opening form asks for. It now asks only the two things a
search cannot run without: the condition and roughly where you are. Your age and
sex are *not* asked up front — they turn up afterwards as "not said" chips you
can fill in if you want to. Asking for them in a form implies they are required;
offering them next to a sentence explaining that a blank produces a question says
what this tool actually does.

## Why I did it this way

**This task looked blocked and is not, and that judgement is the main decision
here.** W2-4 says "correct any *extracted* field", and extraction is W2-1, which
is waiting on an API key. But `docs/PLAN.md`'s pipeline table marks step 2 —
"show profile back as editable chips" — as **deterministic**. The chips do not
need the model; they need something to display. Today that something is what the
user typed. Later it is what the model extracted. The chips do not know or care
which, and that is the point.

**Everything the app believes about the person now lives in one object**
(`web/src/profile.ts`). Before this, the fields lived as six separate pieces of
component state and were assembled into a request at the call site. Now there is
a `Profile`, one function that turns it into a search request, and one function
that describes it as chips. That is what makes W2-1 a *small* task on the day the
key arrives: extraction's entire job becomes "return one of these", and nothing
downstream changes. If I had left the fields scattered, unblocking W2-1 would
have meant rewriting the page as well.

**Every about-you field is `null` when unstated — never zero, never an empty
string, never a default.** This is the single most important line in the module
and it has a comment saying so. A default silently converts "I didn't say" into a
claim the user never made, and the claim it would produce — age 0 — would be an
`NOT_MET` against every adult trial in the registry. That is precisely the
dangerous error `docs/PLAN.md` says to weight hardest.

**The search re-runs when an edit *finishes*, not on every keystroke.** Typing
"41" into the age chip produces the intermediate value 4. Searching on every
change would fire two requests at ClinicalTrials.gov and briefly show the person
results for a four-year-old. So the chips signal separately when an edit is
committed — blur, Enter, Escape, or clicking the × — and only that triggers a
search.

**There is a `useRef` in `App.tsx` holding the latest profile, and it is not
decoration.** React state updates are not visible until the next render, so a
chip that changes a value and immediately says "now search" would search the
*previous* profile. Keeping the current value in a ref alongside the state is the
smallest fix that is obviously correct. The alternative — an effect that watches
the profile and searches when it changes — reintroduces the search-per-keystroke
problem and is harder to explain.

**Chips are buttons with `aria-label`s**, so "Change Age" and "Clear Age, back to
not said" are what a screen reader announces rather than "41" and "×". That is
not a full accessibility pass — W5-3 owns that, and nothing here has been tested
with an actual screen reader — but labelling a bare × control is cheap and I was
not going to ship a control announced as "times".

## What the next run should know

1. **There is still no frontend test framework.** Everything in `web/` is checked
   by the TypeScript compiler, the linter, and me driving a browser by hand. That
   was fine for a skeleton and is becoming less fine: `profile.ts` now contains
   real logic (the null handling above) that deserves a unit test. I have added
   **D-5** for it rather than folding it into this task.
2. **The next `READY` task in file order is W3-1, verdict cards** — and read it
   carefully before starting. Its "reasons with source quotes, nearest site +
   distance" already exist for the *structured* checks, built in W2-2 and W2-3.
   What does not exist is the same treatment for the free-text criteria, which
   needs the judge, which needs the key. It may be genuinely blocked, or it may
   split the way W2-2 did. Decide it on the task's own words, not on mine.
3. **W3-2 (ranking) is fully deterministic and unblocked** — hard conflicts,
   then distance, then phase. All three inputs are already in the search
   response. If W3-1 turns out to be blocked, that is the obvious next thing.
4. **The opening form is temporary and is meant to be replaced**, not extended.
   When W2-1 lands, a free-text box replaces it and hands back a `Profile`. Do
   not add more fields to that form — add them to the profile and they become
   chips automatically.
